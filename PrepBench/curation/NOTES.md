# PrepBench 迁移与评测配置标注准则

本文件说明如何将任务迁移为 DataFrame workload，以及如何根据任务语义标注 `evaluation/config.json`。不在这里维护逐 case 的迁移历史。

- [迁移与审核日志](MIGRATION_LOG.md)：逐 case 的疑问、证据、决定、变更和验证记录。
- [PrepBench README](../README.md)：目录、运行模式、输入可见性及运行入口。

## 1. 迁移范围与资产组织

每个 case 使用 `query.md`、`query_full.md`、`amb_kb.json`、`inputs/`、`reference/solution.py`、`evaluation/config.json` 和 `evaluation/gt/`。运行产物保存在独立的 runs 目录；metadata 记录任务特征，不存审核流程或运行结果。

将 Tableau、Prep Builder、profile pane 等工具操作改为 DataFrame 中性的处理需求；输入已转为 CSV 时，用 input file 描述实际载体。删除依赖缺失截图、特定软件版本或纯可视化交付的要求，保留构成结果表的业务处理。背景中提到 Excel 不意味着必须删除，只有与实际输入或交付约定冲突时才需要调整。

不能把迁移当作重写业务逻辑：计算公式、日期范围、分组粒度、去重、空值和并列规则的变化均需有依据并记入日志。来源文件和导入 manifest 保留溯源作用，不因后续编辑假装它们代表当前版本。

## 2. 需求、澄清与输出契约

`direct` 和 `interact` 使用原始 query.md，`clarified` 使用完整 query_full.md；interact 的完整需求与歧义库留给 simulator。运行时的挂载边界由 runner 控制，不把整份 case 目录交给 agent。

所有模式共同需要的交付约定应在两份 query (query.md / query_full.md) 的 Output 部分明确，包括输出文件名、文件角色、完整列名和固定类别名称。括号属于列名时明确说明。公开类别名称不等于公开每行分类答案。

业务歧义保留在原始 query；query_full 给出完整解释，amb_kb 记录对应澄清及依据。更新后核对二者与 reference/GT 是否一致。`source_text` 应准确引用需求，`intent` 可表达明确规则，`ref` 提供依据，不能伪造原文或填入具体输出答案。

reference/GT 与文字冲突时先记录问题。参考实现里的硬编码、任意顺序或库默认行为不能自动升级为业务要求。没有原始依据时，可以明确提出 benchmark 修订，但要先决定语义再同步资产，不能只在 evaluator 中加特殊补丁。

## 3. 如何标注 evaluation/config.json

### 3.1 先确定输出粒度，再选 key

先用一句话说明每张表“一行代表什么”，再选用于对应记录的字段。例如每个国家、月份、产品一行，key 可由这三个维度组成，Profit 是需要比较的结果值。

- key 来自业务粒度，不来自某份 GT 的偶然唯一性；姓名、日期也不天然唯一。
- 不为躲避数值或分类错误而把结果列加入 key，也不为方便对齐擅自删除有意义的维度。
- 若没有可辩护的记录身份，可以使用全字段对齐，但需保留重复行数量；全字段 key 不是免检。
- 重复 key 不自动等于错误：先看任务是否允许同粒度多条记录。不能靠去重或普通 set 比较丢掉行的重数。
- 身份字段通常应精确比较，不应沿用数值指标的相对容差。规范化会同时影响 key 对齐和内容比较，需审核是否会合并不同身份。

### 3.2 按语义选字段类型

| 字段语义 | 标注选择 | 审核重点 |
| --- | --- | --- |
| 计数、排名、合同月数、明确取整的结果 | `integer` | 数值必须为整数且精确相同；`1` 和 `1.0` 可等价。 |
| 数字外观的编号 | 对象形式 `text_exact` | 保留前导零；只有任务明确将编号定义为整数时才用 integer。 |
| 连续指标或小数结果 | 对象形式 `number` | 精确比较或明确的字段级容差，不按 GT 恰好为整数决定类型。 |
| 精确标签、地址、需保留缩进的文本 | 对象形式 `text_exact` | 避免旧字符串规则剥除有意义的首尾空格。 |
| 任务明确不区分大小写和多余空白的文本 | `text_norm` | 不能用于掩盖地址截断、拼写错误或不同业务类别。 |
| 布尔标记 | `boolean` | 确认任务定义的是布尔值而非有独立含义的文本标签。 |
| 日历日期、一天内时刻、完整时间戳 | `date`、`time`、`datetime` | 不要仅因 CSV 是文本就用 text_exact。 |

新标注优先用显式对象规则，避免不知情地继承旧 `number` 的近似比较和旧文本清理行为。迁移旧字符串配置不是纯格式转换，必须核对规则变化。

### 3.3 精度与容差

没有合理误差依据时，对象 `number` 使用零容差。计数、排名、整数金额及明确舍入后的结果通常应精确比较；不要全局指定 2% 或 0.5%。

连续计算确需允许浮点误差时，根据输出精度、字段单位和计算方式选择 `abs_tol`、`rel_tol`，记录依据。相对容差在 GT 为零时不能提供有效误差预算；接近零的指标尤其需要审核绝对容差。具体公式见公共协议。

容差不能修复比例乘 100、年龄差一岁、少算一项、单位错误或错误舍入口径。比如要求输出四舍五入两位小数的比例，应检查该舍入结果，不是因为存在小数就给百分比级误差。

### 3.4 日期时间和空值

任务未要求字面输出格式时，按解析后的日期/时间比较。datetime 内置接受常见 ISO 表示；`formats` 用于追加任务特有的表示，例如 `%d/%m/%Y %H:%M:%S`。不要每个 case 重复枚举内置 ISO 格式。

日/月含义需要任务依据，不能同时加入相互矛盾的格式后取第一个成功结果。当前 evaluator 会拒绝产生多个不同解释的值。时间值不同、非法时间、缺失日期不能通过删秒、去时区或补默认年份来掩盖。时区和更高精度等未支持需求先记覆盖限制。

如果任务确实要求精确字符串格式，需要另外明确评分方式；`formats` 本身不是输出格式约束。完整日期标签包含星期等必须保留的文本时，也不能解析后丢掉信息。

按列决定 `null_values`。数值列可在有依据时接受空字符串、`nan` 等等价序列化，文本中的 `NA` 可能是有效内容，不能全局映射。GT 有有效值而候选为空仍应失败；“允许空值”不等于“空值可匹配任意结果”。空字符串有业务含义时考虑 `null_values: []`。

### 3.5 顺序要求

只有明确且经过审核的任务顺序要求才评分。GT 的偶然排列、reference 的稳定输出不是充分依据。完整 query 新增但原始 query 未明确的顺序，需要确认它是合法澄清还是不必要的实现细节。

需要字段排序时，使用 `ignore_order: false` 和明确的 `order_by`，注明方向、空值位置及有业务意义的次级排序。排序前先确认 GT 自身满足要求。无顺序要求时不启用检查。

key 与排序字段不同：key 用于确定记录身份，order_by 用于检查输出排列。并列项只在所有要求的排序字段相等时允许互换，不能从 key 自动增加次级排序，也不能先替 candidate 排序再验收。

“保留输入顺序”不是“按某列排序”。当前字段排序协议不能直接表达依赖输入行位置的所有要求；先记录覆盖缺口，不用错误的排序规则替代，也不把内容通过称为完整验证。

### 3.6 配置示例

假设任务明确要求每个门店每月一行，按月份、门店升序，Sales 为整数销量，Margin 为明确舍入后的比例，可写为：

```json
{
  "files": {
    "output_01.csv": {
      "key": ["Store", "Month"],
      "columns": {
        "Store": {"type": "text_exact", "null_values": []},
        "Month": {"type": "date", "formats": ["%d/%m/%Y"]},
        "Sales": {"type": "integer"},
        "Margin": {"type": "number", "abs_tol": 0, "rel_tol": 0}
      },
      "ignore_order": false,
      "order_by": [
        {"column": "Month", "direction": "asc", "nulls": "last"},
        {"column": "Store", "direction": "asc", "nulls": "last"}
      ]
    }
  }
}
```

这只是有明确前提的示例，不是全部 case 的通用模板。列名、粒度、精度和顺序都需逐题决定。

## 4. 验证与失败后的处理

先做资产检查：配置合法、输出 schema 与 GT 对应、GT 类型和顺序有效、reference 在固定环境中复现 GT。GT 自比通过只能说明配置接受它，不能证明业务正确。对重要规则选少量应通过和应失败的反例，例如 Time 补零应通过，比例乘 100 或复制一行应失败。

随后用 interact 跑 pandas 和两个不重复的抽样后端，保留代码、问答、输出和报告。记录抽样选择并平衡覆盖，不通过反复换后端筛出好结果。三个后端都通过后仍检查评测覆盖；真实 agent 失败不妨碍任务完成审核。

| 失败原因 | 应修改什么 | 不应做什么 |
| --- | --- | --- |
| 等价表示被拒绝、字段规则错误 | evaluator/config，并用正反例验证 | 只对失败 backend 特判或放宽真实数值差异 |
| 需求、reference、GT 不一致 | 先决定任务语义，再同步相应资产并记日志 | 把 reference 或多数候选自动当作真值 |
| simulator 回答错误或不一致 | 澄清资产或 simulator，随后新生成 | 将错误回答造成的失败全部归咎于代码 |
| agent 算错、忽略正确澄清、API 用错 | 保留失败及证据 | 增加容差、删比较列、改 key 使它通过 |
| provider、网络或执行环境失败 | 单独记录，按原因重试 | 计作业务语义错误或无记录地反复重跑 |

错误代码只是定位线索。例如 KEY_MISMATCH 可能来自错误分类、字段格式、文件写反或记录缺失，不能仅凭错误码决定改配置。

修改 config/evaluator 可离线重评冻结 CSV，并对比较中的各后端使用同一规则。修改 query、amb_kb、simulator 后需新建 generation run；更新 query 不会自动修正旧 CSV。若修改 GT，要记录依据和版本，重新核对 reference，再决定重评还是重新生成。

临时重命名候选列等诊断可以用于发现后续问题，但不能覆盖正式输出或记为 agent 通过。已知覆盖缺口、待决语义、所用资产版本和运行编号记录在迁移日志中，正式实验前冻结资产。

## 5. 日志维护

按 [MIGRATION_LOG.md](MIGRATION_LOG.md) 的格式记录具体 case。准则发生变化时修改本文件；evaluator 的实际行为变化时更新公共协议；个别 case 的决定只进入日志及对应任务资产，避免三处重复维护。

# PrepBench 任务整理指南

本指南面向导入、审核和修改 PrepBench。第一次整理任务时，按第 3 节执行；配置评估时查第 4 节；出现失败或修改资产后查第 5 节。

- [PrepBench README](../README.md)：安装、运行命令、实验模式和结果文件。
- [公共评估协议](../../evaluation/README.md)：evaluator 实际支持的类型、容差、排序和错误代码。
- [迁移与审核日志](MIGRATION_LOG.md)：逐 case 的依据、决定、验证结果和已知限制。

## 1. 目标与完成标准

整理一个 case，是把原始任务变成能够在本仓库独立运行和评估的 DataFrame workload。需要交付任务资产、明确的输出契约、验证证据，以及尚未覆盖的要求。

“整理完成”不等于“所有 agent 都通过”。真实的计算或交互失败可以保留；如果需求 `query.md` 与 Ground Truth （GT） 的核心含义仍有冲突，则应标为待决定，而不是通过放宽评估宣布完成。仅将 evaluation 配置对 GT 对比通过（将 evaluation 协议对 ground truth 的表格生成结果）或三个 backend 通过，也不能证明任务契约正确。

一个完成本轮审核的 case 应满足：

- 输入、题面、澄清规则、reference、GT 和评估配置齐全，关键业务规则一致。
- reference 能在指定环境中复现 GT；重要规则经过独立核算或有针对性的正反例验证。
- 已按计划执行真实 interact，记录成功、失败或其他问题；未完成的验证明确标注。
- 日志能说明改了什么、为什么改、用了哪版资产和哪些 run，以及评分未覆盖什么。

迁移是尽可能忠于原有 PrepBench 内容，不是重写业务逻辑。公式、日期范围、分组、去重、缺失处理、并列排名等变化都需要依据。确需调整任务契约时才做调整。

## 2. 文件结构与可见性

每个任务放在 `PrepBench/case_XXX/`。GT 指 ground truth，即评估用的预期输出。

| 文件 | 作用与可见性 | 修改后重点核对 |
| --- | --- | --- |
| `metadata.yaml` | 任务领域、输入表数和列数；不存审核结论 | 是否与输入结构一致 |
| `inputs/` | agent 可以读取的输入 CSV | query、reference、GT 及受影响的规则 |
| `query.md` | 初始需求；direct 和 interact 的 agent 可见 | 必要业务规则与偏好要求是否明确、输出约定、KB 的原文引用 |
| `query_full.md` | 完整需求；clarified 的 agent 可见，interact 时仅 simulator 可见 | KB、reference、GT 和评分范围 |
| `amb_kb.json` | 私有澄清知识库，供 simulator 使用 | 与两份 query 的关系、规则依据及引用准确性 |
| `reference/solution.py` | 私有参考实现，供研究者验证及 simulator 理解规则 | 完整需求、输入、GT；实现习惯是否被误当作要求 |
| `evaluation/gt/` | 私有预期输出 | 来源、计算依据、schema、精度和重复行 |
| `evaluation/config.json` | 私有评分规则 | key、类型、容差、空值、顺序是否符合已决定的契约 |
| `runs/` | 每次生成、交互、候选输出与评估记录 | 资产版本、运行编号、生成与评估两个阶段的状态 |

生成阶段只给 agent 当前模式允许的 query、文档和输入。不要挂载整个 case、GT、reference、config、KB 或审核记录。interact 的 simulator 可以使用私有材料回答问题，但这些材料不直接交给解题 agent。使用现有 runner 维持隔离边界，评估在生成结束后单独进行。

## 3. 一个 case 的整理流程

### 第一步：确认工作位置与来源

在约定的仓库根目录执行命令，先确认当前目录、分支和已有未提交修改。实验使用当前目录的 `.venv`、agent 配置和 simulator 配置；必要时传入绝对路径，避免误用另一个 worktree 的文件。

查找原始 query、完整需求、amb_kb.json、输入，以及可能位于其他目录的 reference、GT、config。记录来源路径和文件哈希，原资产保持只读。导入记录描述的是来源版本，不能在后续修改后将它当作当前资产版本。保留已有研究文件和运行产物。

### 第二步：审查需求和输出契约

先说明每张输出表“一行代表什么”，再检查过滤、聚合、关联、并列、缺失和输出规则。至少对照 query、query_full、amb_kb.json、reference、GT，特别标出仅在完整需求或实现中出现的精度、排序、空白和固定标签要求。

必要业务规则和影响答案的偏好要求应尽量写进 query，使 query、query_full、KB、reference、GT 和评分规则保持一致。例如温差是否保留符号、是否只检查在职员工、half-to-even 舍入。不能仅因 query 省略公式或细节就一律补齐；没有明确误导的细节可继续保留在 full/KB，已明确决定不补充的逐题事项按迁移日志执行。

公开的是有依据的任务规则，不是参考代码、具体输出答案或库默认行为。full/GT 本身有冲突时先审查依据，不机械地把 full 全文搬入 query。一般等价输出表示继续兼容。已运行题目的 query/KB 改变后必须另起生成，旧资产和原结果保留；旧通过记录不代表已按修改后的要求重新验收。

所有模式共同需要的交付约定，应在两份 query 的 Output 部分明确：文件名、文件角色、完整列名及约定的固定类别名称。括号属于列名时也要保留。公开类别名称不等于公开每行答案。

amb_kb.json 的 `source_text` 必须准确引用需求，`intent` 用于表达明确规则，`ref` 提供依据。迁移或修改题面后重新检查引用；不要伪造原文，也不要填入具体输出答案。

reference 的硬编码、库默认行为和 GT 的偶然排列都不是独立的业务依据。例如：

- 023 曾要求 Scent 带一个尾部空格；决定取消后，同步修改完整需求、amb_kb.json、reference 和 GT，仍保留精确文本评分。
- 051 的 reference 曾硬编码场馆顺序；题面无此要求，因此删除该实现细节，评估不检查行序。

发现冲突先决定语义、记录依据，再同步资产。不要只在 evaluator 中增加特判。

### 第三步：导入并做必要的题面清理

建立第 2 节的标准目录。将 Tableau、Prep Builder、profile pane 等操作改为 DataFrame 中性的处理需求；实际提供 CSV 时使用 input file 等准确描述。删除依赖缺失截图、软件版本或纯可视化交付的要求，保留业务计算及有用的概念示例。

背景提到 Excel 不一定需要删除；只有与实际输入或交付冲突时才调整。修正明显的前后矛盾，例如 022 的 Context 写“之前七天”，Requirements 写“当天及之前六天”，应统一窗口含义。

metadata 只记录任务特征。审核决定写入迁移日志，避免把研究过程混入 agent 题面。

### 第四步：配置评估并验证资产

按第 4 节选择 key、类型、容差和顺序。已有 config 也要审核，不直接继承旧的全字段 key、百分比容差或文本清理规则。

| 验证层次 | 要回答的问题 | 不能据此证明什么 |
| --- | --- | --- |
| GT 自比、配置和 schema 检查 | evaluator 能否接受预期资产？ | GT 是否算对、业务契约是否合理 |
| reference 在固定环境中复现 GT | 参考实现是否与 GT 一致？ | 二者没有共同错误 |
| 独立核算、正反例检查 | 关键业务规则和评分边界是否有效？ | 当前数据没有触发的所有情况都正确 |
| 真实 interact | agent 能否通过交互获得规则并实现任务？ | simulator 每次都一致、通过即覆盖全部要求 |

优先围绕关键规则选少量有区分力的检查，不机械堆测试。例如 051 独立按“排名 = 1 + 分差更大的比赛数”核算，并确认 dense rank、按场馆内部排名和反向排名会被拒绝。也要检查当前数据是否实际包含并列、缺失、重复或舍入边界。

这些检查在模型运行前完成，可以避免把资产错误误判为 agent 错误。reference 验证使用研究者侧环境，与 agent 生成容器分开；命令和环境说明见 README。

### 第五步：执行 interact 并检查结果

默认先运行 pandas，再从 Polars、Ibis、PySpark 中抽取两个不重复后端。记录随机种子和抽样结果，后续适当平衡覆盖；不要通过换后端或重复运行筛出通过结果。验证同一 case 的后续修订时，优先沿用之前的后端。

比较各后端时固定任务版本、agent 模型及 reasoning 设置、模式、Docker 镜像和 simulator 设置。镜像尽量记录具体 ID；本地配置记录非敏感设置或指纹，不把凭据写进日志。

保留候选代码、CSV、交互问答、generation/evaluation 阶段记录和 `result.json`。生成完成仅表示产物生成成功；是否正确要看正式评估。读问答确认关键规则是否真正传达。没有模型服务或环境条件时，记录阻塞，不能用单元测试替代真实运行结论。

### 第六步：记录与收尾

将最终规则、改动、验证结果和限制写入迁移日志。完成一个 case 后即可按协作约定提交，无需等所有 case 都结束；是否 commit/push/创建 PR 依当前任务授权执行。

## 4. 评估配置规则

### 4.1 输出粒度与 key

key 用于对应同一条业务记录，不用于规定输出顺序。例如每个国家、月份、产品一行，key 可以是这三个维度，Profit 是需要比较的结果值。

- 依据业务粒度选 key，不依据 GT 恰好唯一；姓名、日期并非天然唯一。
- 不为躲避数值或分类错误而把结果列加入 key，也不擅自删除有意义的维度。
- 没有可辩护的记录身份时，可以全字段对齐，但必须保留重复行数量。
- 重复 key 不自动等于错误；不能通过去重或普通 set 比较丢失行的重数。
- 身份字段一般精确比较。规范化同时影响 key 和内容，需防止合并不同身份。

### 4.2 字段类型与文本

新配置使用显式对象规则。旧字符串规则可能隐含近似比较或首尾空白清理，转换前应检查行为差异。

| 字段语义 | 标注选择 | 注意事项 |
| --- | --- | --- |
| 计数、排名、合同月数、明确取整结果 | `integer` | 精确整数；`1` 和 `1.0` 可等价，小数部分非零不接受 |
| 数字外观的编号 | `text_exact` | 保留前导零，不因外观像数字就用 integer |
| 连续指标、小数结果 | `number` | 指定字段级精度，不按 GT 恰好是整数决定类型 |
| 精确标签、姓名、地址、需要保留空白的文本 | `text_exact` | 对象规则不会自动删除首尾空格 |
| 明确允许忽略大小写和多余空白的文本 | `text_norm` | 不用于掩盖拼写、截断或类别错误 |
| 布尔标记 | `boolean` | 确认字段表达真/假，而非独立标签 |
| 日期、一天内时刻、完整时间戳 | `date`、`time`、`datetime` | 不因 CSV 以文本保存就全部使用 text_exact |

题目要求文本无首尾空格时，先确保 reference/GT 已按契约清理，再使用 `text_exact` 验证。不要无条件规范化所有文本，让真正的清理错误也通过。

### 4.3 数值精度与容差

先决定要验证什么，再设置容差：

| 评分目标 | 推荐做法 | 评分边界 |
| --- | --- | --- |
| 精确计数、排名或整数金额 | `integer` | 不允许加减 1 等真实误差 |
| 精确比较已舍入的数值结果 | `number`，零容差 | 可拒绝不同舍入结果，但不检查代码使用了哪种算法或 CSV 是否补足末尾零 |
| 接受指定数值精度内的结果 | `number`，有依据的 `abs_tol`/`rel_tol` | 可以接受未舍入值，不再严格验证指定舍入规则 |

没有合理误差依据时，number 尽量使用零容差。在合理范围内，也可以允许误差，比如 query_full 保留两位小数但 query 未明确的场景，因为 query_full 是 PrepBench 造出来的完整需求，并未原始真正需求，而 query 才是原始需求。

本项目的例子：

- 021 两个平均费用、022 移动平均销售额采用 `abs_tol: 0.005, rel_tol: 0`，接受相对两位小数 GT 不超过半分钱的差异。原始 query 未规定两位小数，本轮决定按数值精度评分；query_full 有小数的舍入要求。
- 051 平均排名采用 `abs_tol: 5e-10, rel_tol: 0`，依据 GT 九位小数的半个末位单位，允许高精度的未舍入均值。场次和最佳/最差排名仍精确比较。

这些是有记录的逐题决定，不能把所有小数列统一设为 `0.005`，也不能恢复全局 2% 容差。若目标是验证 HALF_UP 等指定规则，应使用能触发差异的数据并比较正确舍入结果；容差可能接受另一个舍入结果或未舍入值，必须说明这一限制。

边界检查应包含应通过的等价表示，以及刚超出容差的错误值。单位错误、比例乘 100、少算一项、错误窗口或错误排名都不能靠容差消除。

### 4.4 日期时间与空值

无字面格式要求时，比较解析后的日期/时间。`formats` 用于追加任务特有格式，**不是限制输出必须使用该格式**；内置支持的等价 ISO 表示仍可能通过。不要重复枚举内置格式。

日/月含义必须有依据，不同时加入相互矛盾的格式后取第一个解释；当前 evaluator 会拒绝产生不同解释的值。不能通过删秒、去时区或补默认年份掩盖真实时间差异。未支持的时区、精度等要求记录为覆盖限制。

若要求精确字面格式，另行决定评分方式。包含星期的完整日期标签不能解析后随意丢掉文字信息。选择暂按日期值评分时，要明确完整需求中的字面格式尚未验证。

按列决定 `null_values`。数值字段可以在有依据时接受空字符串、`nan` 等等价表示；文本 `NA` 可能有实际含义，不能全局映射为空。需要保留字面文本或空字符串时考虑 `null_values: []`。GT 有值而候选为空必须失败。

输入缺失规则与输出空值规则分别检查。例如 051 的 `-` 是输入半场比分的缺失标记，不意味着所有输出字段都应把 `-` 当成空值。

### 4.5 顺序

只检查经过审核的明确顺序要求。GT 的排列、reference 的稳定输出以及 simulator 临时增加的排序要求，都不足以单独作为依据。

需要排序时使用 `ignore_order: false` 和 `order_by`，明确方向、空值位置和必要的次级字段，先确认 GT 自己符合规则。无要求时忽略顺序。并列项只在所有要求的排序字段相等时允许互换，不从 key 自动增加次级排序，也不先替 candidate 排序再验收。

区分计算顺序和最终行序：022 的窗口计算必须按真实日期进行，不意味着最终 CSV 也必须按同一顺序评分。“保留输入顺序”也不等于“按某列排序”；当前字段排序协议不能直接表达的要求应记录缺口，不用其他排序冒充。

### 4.6 配置示例

假设每个门店每月一行，Sales 是整数销量，Margin 需要精确比较舍入结果，且任务明确要求按月份、门店升序：

```json
{
  "files": {
    "output_01.csv": {
      "key": ["Store", "Month"],
      "columns": {
        "Store": {"type": "text_exact", "null_values": []},
        "Month": {"type": "date", "formats": ["%d/%m/%Y"]},
        "Sales": {"type": "integer"},
        "Margin": {"type": "number", "abs_tol": 0, "rel_tol": 0}
      },
      "ignore_order": false,
      "order_by": [
        {"column": "Month", "direction": "asc", "nulls": "last"},
        {"column": "Store", "direction": "asc", "nulls": "last"}
      ]
    }
  }
}
```

这是有前提的示例，不是可直接复制到所有 case 的模板。

## 5. 结果诊断与修改后复验

### 5.1 先定位失败原因

结合题面、问答、代码和正式报告判断；错误代码只是线索。例如 `KEY_MISMATCH` 可能来自标签、格式、文件写反或记录缺失，不能仅凭错误码改 key。

| 情况 | 处理方式 |
| --- | --- |
| 等价表示被拒绝、字段规则错误 | 修正 config；仅共享比较机制确有问题时才改 evaluator，并验证正反例 |
| 需求、reference、GT 冲突 | 先决定契约，再同步受影响资产；不把多数候选自动当成真值 |
| simulator 错答或无依据增加规则 | 修正澄清资产或 simulator，重新生成；不能全归咎于 agent |
| agent 未取得关键澄清 | 检查是否问过、是否被拒绝、澄清预算是否耗尽、规则是否可合理获得，再决定是否修订任务 |
| agent 算错、忽略已获得的正确澄清、API 用错 | 保留真实失败，不删列或放宽数值规则使其通过 |
| LLM provider、网络或环境失败 | 单独记录原因，必要时重试；不计作业务语义错误 |

### 5.2 根据改动选择复验方式

| 修改内容 | 需要的复验 |
| --- | --- |
| 仅 config 或 evaluator | 用同一新规则重评各后端冻结 CSV，检查相关正反例；不必重新生成 |
| query、query_full、KB 或 simulator 行为 | 新建 generation run 才能验证新任务下的交互/生成；旧输出只能作为历史或诊断证据 |
| reference 或 GT | 记录依据和版本，核对逐字段/逐行差异并重新验证 reference；若契约变化，同步需求后新生成 |
| 输入数据 | 重新核对契约、reference/GT 和配置，并新生成候选 |

每个 run 保留原始代码、CSV 和问答。临时改列名、交换文件或清理文本可以帮助定位，但不得覆盖正式候选，也不得将修补后的结果记为 agent 通过。

正式重评会更新 evaluation/result；更新前保存旧报告及配置版本，或将诊断报告另存。记录资产哈希、run 编号和评估版本，明确表格采用旧结果还是新结果。不要把旧题面输出通过新 config 称作“新题面 interact 通过”。

所有后端通过后仍检查覆盖边界。例如连续日期数据不能验证遇到缺日时的窗口语义；当前没有重复行也不能证明实现保留了重复。记录这些限制，不为了审核而无依据扩充任务。

## 6. 记录和提交清单

每个 case 在 [MIGRATION_LOG.md](MIGRATION_LOG.md) 中简要记录来源、关键疑问、最终决定、资产改动、验证及已知限制。运行表写清 backend、run、资产/评估版本和状态。通过、失败、评估跳过、未运行应区分；生成失败不等于已评估的内容错误。

提交或交接前检查：

- [ ] 任务文件齐全，schema、metadata、amb_kb.json 引用与最终资产一致。
- [ ] reference/GT 和关键正反例已经验证，真实运行或阻塞有记录。
- [ ] 精度、日期字面格式、顺序及未触发分支等限制明确，不夸大通过含义。
- [ ] 仅暂存目标 case 的输入、query、amb_kb.json、metadata、reference、config、GT，以及相关说明文档。
- [ ] 不提交 `runs/`、`output/`、虚拟环境、本地 agent/simulator 配置、凭据或临时审核快照；本地证据保留，不随意删除。
- [ ] 检查暂存 diff，保护其他合作者的未提交文件；日志中引用的本地证据注明用途，不当作仓库运行依赖。
- [ ] 确认提交所在分支及后续工作目录；跨 worktree 交接时核对独有资产、配置和环境，切换目录或分支本身不会更新代码。

按一个 case 或一批完整改动提交即可。共享的迁移准则放在本指南，逐题决定放在迁移日志，evaluator 实际行为放在公共协议；保持三者分工，避免复制大量历史记录或增加不必要的流程。
